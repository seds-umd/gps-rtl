# GPS receiver status, November 2026

What changed after `status-2026-09.md`, which is still the place to read for
the wider picture. In short: the regression now runs natively on Windows, the
acquisition core has been built for and run on a board for the first time from
the current tree, and doing that exposed two real problems in fine and coarse
acquisition. Both are fixed and measured on the board.

## The bug: code removal locked two chips early

`RemovePrn` computed (PRN phase - sample timestamp - phase offset) modulo 4092
as one 13-bit subtraction with a single wrap. The difference reaches -8182, so
whenever phase offset + timestamp exceeded PRN phase + 4092 it overflowed and
the alignment locked eight samples early. Coarse acquisition still reported the
right code phase; the fine stage then correlated against a PRN two chips off,
found nothing, and reported a noise-level metric with a meaningless frequency.

A model of the old arithmetic with uniformly random code phase and timestamp
mis-locks in 46.6% of cases, always by those eight samples; the fixed
arithmetic in none. This is very likely the "only detecting 5 SVs at best when
python code is detecting 8" note at the top of `AcquisitionModular.scala`.

It was not caught earlier because the only bench that exercised the real-time
alignment path (`GpsTop`, `debug = false`) used a code phase of 37, and
`RemovePrn`'s own bench happened to use combinations where the timestamp
wrapped before the false lock. The board self-test found it on its second
signal. `RemovePrn`'s bench now has a case that fails on the old code.

## The second problem: 4096-point FFT, 4092-sample code

This was the other historical note ("sample phase isn't constant between
runs"). A coarse frame was 4096 consecutive samples of a code that repeats
every 4092, so the circular correlation saw the code wrap four samples early.
That gives two peaks four samples apart, weighted by where the code boundary
falls in the frame. Near the middle they merge into a flat top five samples
wide at half height: up to 6 dB of coarse sensitivity lost, and a reported
phase that could land anywhere on the flat top.

The fix stretches one 4092-sample period over the 4096 points, for the signal
and the replica alike, by repeating one sample at the start of each block of
1024. The frame is then exactly periodic, the correlation has a single peak,
and the worst case is the quarter chip of one repeated sample (1.2 dB). No
sample is dropped and the live stream is not slowed: the repeat goes out on the
next clock. Coarse bins become exactly 1 kHz instead of 999 Hz.

Measured on the board, same satellite acquired 392 times in a row with no
noise:

| Phase error (samples) | -2 | -1 | 0 | +1 | +2 | Weakest metric |
| --- | --- | --- | --- | --- | --- | --- |
| Before | 34 | 78 | 163 | 106 | 11 | 134 |
| After | 0 | 4 | 388 | 0 | 0 | 255 |

Detection with the emulator's noise source (single 1 ms coherent search, signal
on a coarse bin). "Found" means the right frequency bin and a phase inside the
build's own accuracy: two samples before, one sample after.

| Signal | Before, of 40 sweeps | After, of 60 sweeps | Metric before to after (median) |
| --- | --- | --- | --- |
| about 51 dB-Hz | 40 | 60 | 25 to 35 |
| about 45 dB-Hz | 25 | 59 | 14 to 16 |
| about 43 dB-Hz | 18 | 36 | 11 to 13 |
| about 40 dB-Hz | 4 | 10 | 7 to 8 |
| noise only | no metric above 4 | no metric above 4 | |

So a single search is now dependable down to about 45 dB-Hz. Live-sky signals
are mostly 35 to 50 dB-Hz, so the strongest satellites should acquire, but the
weaker ones need more than one 1 ms coherent search: non-coherent summing over
several windows is the next step for sensitivity. A Doppler half a coarse bin
off still costs up to 3.9 dB; that is separate and unchanged.

real FFT core's latency and back-pressure rather than the C model's (step 4 of

## Other fixes along the way

- `Prn` renamed to `PrnGenerator`: Windows reserves the name and git would not
  check the repository out at all.
- `fpga-utils` `run_wrapper` now regenerates Verilog when any Scala source is
  newer, not just the ones a bench lists. A fix to a submodule could previously
  be "tested" against stale Verilog and appear not to work, or appear to.
- `fpga-utils` finds `sbt.bat` on Windows.
- `gps-model` loads the Windows build of the FFT model and accepts the two
  fields newer releases added to its settings structure.
- Two tests assumed NumPy's default integer is 64 bits; it is 32 on Windows.

## Not done

- Nothing here touches a real MAX2769. The emulator stands in for the serial
  format and timing only; pin timing, reset sequencing against a running clock
  and SPI configuration on the dev board are still open.
- No live-sky capture, tracking, navigation or host transport beyond the test
  UART.
- The self-test bitstream was built and run for the S7-25 only. The script
  accepts `--variant s7-50` but that has not been built.
- CI still has no runner.
- An independent review of the new RTL also noted that `MaxInterface` takes
  its serial-domain reset asynchronously. The self-test keeps the emulator
  silent for 256 serial clocks after reset so every flop is holding its reset
  value at release; a real front end that is already clocking data needs a
  reset synchronizer there.

## Next steps, in order

1. Repeat the April 2025 dev-board test with this tree: MAX2769 board on an
   Arty PMOD, `GpsTop` in place of the capture path, the self-test UART for
   results. The emulator's serial output can be brought out to a PMOD first to
   check the pin mapping with a loopback wire.
2. Non-coherent accumulation over several coarse windows, to reach live-sky
   signal levels below 45 dB-Hz.
3. Discard an acquisition in the core when `sample_overflow` sets during it,
   instead of leaving that to the host.
4. Tracking, board integration and the OBC loader, as in the September list.
