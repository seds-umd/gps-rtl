# GPS receiver status, November 2026

What changed after `status-2026-09.md`, which is still the place to read for
the wider picture. In short: the regression now runs natively on Windows, the
acquisition core has been built for and run on a board for the first time from
the current tree, and doing that exposed one real bug (fixed) and one design
limit (measured, not fixed).

## The bug: code removal locked two chips early

`RemovePrn` computed (PRN phase - sample timestamp - phase offset) modulo 4092
as one 13-bit subtraction with a single wrap. The difference reaches -8182, so
whenever phase offset + timestamp exceeded PRN phase + 4092 it overflowed and
the alignment locked eight samples early. Coarse acquisition still reported the
right code phase; the fine stage then correlated against a PRN two chips off,
found nothing, and reported a noise-level metric with a meaningless frequency.

A model of the old arithmetic with uniformly random code phase and timestamp
mis-locks in 46.6% of cases, always by those eight samples; the fixed
arithmetic in none. This is very likely the "only detecting 5 SVs at best when
python code is detecting 8" note at the top of `AcquisitionModular.scala`.

It was not caught earlier because the only bench that exercised the real-time
alignment path (`GpsTop`, `debug = false`) used a code phase of 37, and
`RemovePrn`'s own bench happened to use combinations where the timestamp
wrapped before the false lock. The board self-test found it on its second
signal. `RemovePrn`'s bench now has a case that fails on the old code.

## The limit: 4096-point FFT, 4092-sample code

Not a bug in the RTL, but the reason for the other historical note ("sample
phase isn't constant between runs"). The circular correlation is 4096 points
long and the code repeats every 4092 samples, so the code wraps four samples
early inside the window. That gives two correlation peaks four samples apart,
weighted by where the code boundary falls. Near the middle of the window they
merge into a flat top five samples wide at half height.

Measured on the board, same satellite acquired 392 times in a row:

| Phase error (samples) | -2 | -1 | 0 | +1 | +2 |
| --- | --- | --- | --- | --- | --- |
| Count | 27 | 85 | 165 | 108 | 7 |

Consequences:

- `phase_offset` is good to half a chip, not one sample.
- Coarse sensitivity varies by up to 6 dB with the timing of the capture window.
- A two-sample error costs the fine stage about 6 dB: the metric on a clean
  signal falls from 255 to about 135.

Sensitivity as measured with the emulator's noise source (single 1 ms coherent
search, signal exactly on a coarse bin):

| Signal | Outcome over three sweeps |
| --- | --- |
| about 51 dB-Hz | found every time, metric 25 to 35 against 4 for absent satellites |
| about 45 dB-Hz | found twice, missed once |
| about 40 dB-Hz | never found |
| noise only | no metric above 4 |

Live-sky signals are mostly 35 to 50 dB-Hz, so this core as it stands will
only acquire the strongest satellites. Making the code period and the FFT
length agree (for example by repeating four samples of both the signal and the
replica so that one code period fills the 4096 points) should recover most of
the 6 dB and the phase accuracy; non-coherent summing over several windows
would add more. Neither has been tried.

## Board evidence (November 11, 2026)

Arty S7-25 (xc7s25csga324-1), Vivado 2025.2, final bitstream SHA-256
`ddb73ce8d69648d69a3633d11361280253f37becade38eab1e7c79046db94705`.
Full results and source revisions: `docs/evidence/arty-s7-25-selftest-2026-11-11.md`.

| Measure | Result |
| --- | --- |
| Timing, 50 MHz system clock | met, worst setup slack 1.218 ns, worst hold slack 0.080 ns |
| Timing, 16.368 MHz serial clock | met, 41.9 ns slack |
| Clock-domain crossings | 729 paths, each bounded to 8 ns, all met |
| Utilization | 3,827 LUTs (26%), 4,069 registers (14%), 7.5 block RAM tiles (17%), 11 DSP slices |
| `GpsTop` alone | 2,445 LUTs, 3,031 registers, 7.5 block RAM tiles, 9 DSP slices: inside an XC7S15's 8,000 LUTs, 10 tiles and 20 DSP slices, but tight on block RAM |
| Noiseless signals | satellite, frequency and phase correct for every case: both +/-23 kHz search edges, a Doppler between fine bins, two satellites at once, and ten code phases either side of each 4096/4092 mapping step |
| Restarts | ten independent restarts, same frequency, phase within one sample of each other |
| Continuous run | 12,544 results in 300 s, no wrong result, `sample_overflow` never set |

The continuous run is the first measurement of the serial boundary against the
real FFT core's latency and back-pressure rather than the C model's (step 4 of
the September list), for a 50 MHz system clock and a 16.368 MHz serial clock.

## Other fixes along the way

- `Prn` renamed to `PrnGenerator`: Windows reserves the name and git would not
  check the repository out at all.
- `fpga-utils` `run_wrapper` now regenerates Verilog when any Scala source is
  newer, not just the ones a bench lists. A fix to a submodule could previously
  be "tested" against stale Verilog and appear not to work, or appear to.
- `fpga-utils` finds `sbt.bat` on Windows.
- `gps-model` loads the Windows build of the FFT model and accepts the two
  fields newer releases added to its settings structure.
- Two tests assumed NumPy's default integer is 64 bits; it is 32 on Windows.

## Not done

- Nothing here touches a real MAX2769. The emulator stands in for the serial
  format and timing only; pin timing, reset sequencing against a running clock
  and SPI configuration on the dev board are still open.
- No live-sky capture, tracking, navigation or host transport beyond the test
  UART.
- The self-test bitstream was built and run for the S7-25 only. The script
  accepts `--variant s7-50` but that has not been built.
- CI still has no runner.
- An independent review of the new RTL also noted that `MaxInterface` takes
  its serial-domain reset asynchronously. The self-test keeps the emulator
  silent for 256 serial clocks after reset so every flop is holding its reset
  value at release; a real front end that is already clocking data needs a
  reset synchronizer there.
